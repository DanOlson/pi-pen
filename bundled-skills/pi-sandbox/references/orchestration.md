# Orchestration

## Shape the workflow around dependencies

Parallelize only independent work. A useful feature workflow is:

1. Run focused investigations concurrently when they answer distinct questions.
2. Synthesize their evidence into one implementation assignment.
3. Give one implementation agent ownership of tests, code, validation, and
   commits in its worktree.
4. After it commits, run a reviewer in the same worktree against that commit.
5. Have the reviewer inspect the diff and run useful checks without editing.
6. Send actionable findings back to the same implementation session for
   test-first corrections and another commit.
7. Independently verify the final commit and integrate it only when authorized.

Implementation and review are sequential, so they do not need separate
worktrees: a headless run's worktree lock is released when it exits, and the
reviewer then sees the commit, the branch, and anything the implementer left
uncommitted, which is itself a finding. Give the reviewer the base and
candidate commits and the guardrails in the prompting reference, and check
`git status --porcelain` from the host afterwards; a reviewer with `bash` can
modify the tree even without an edit tool.

Use a separate worktree for review only when it buys something: several
reviewers at once (the lock allows one headless run per worktree), or a
reviewer you would rather not let near the implementer's tree before the
revision. Then create it detached at the exact commit with
`git worktree add --detach <review-path> <sha>`, confirm with
`git -C <review-path> rev-parse HEAD`, and expect it to rebuild from scratch:
`target/`, `node_modules/`, and similar directories are worktree-local.

## Worktree plus shared namespace, end to end

This is the complete sequence for one implementer and one reviewer once the
namespace in `SKILL.md` is set up and authenticated. All three runs use the
implementer's worktree; they never overlap in time. Paths are examples.

```text
# Once per batch, from the main checkout.
pi-sandbox namespace show                      # must say: pi credentials present
pi-sandbox build                               # so workers reuse one image
mkdir -p -m 0700 /private/tmp/batch-42
BASE=$(git rev-parse HEAD)

# Implementer: its own branch and worktree.
git worktree add -b agents/feature-42 /private/tmp/wt-implement "$BASE"
pi-sandbox exec --prompt-file /private/tmp/batch-42/implement.prompt \
  --new-run-under /private/tmp/batch-42 --run-name implement --timeout 1800 \
  -- --provider PROVIDER --model MODEL
# (run from /private/tmp/wt-implement; the controller sets cwd)

# Reviewer: same worktree, after the implementer has exited and committed.
git -C /private/tmp/wt-implement rev-parse HEAD     # the candidate commit; put it in the prompt
git -C /private/tmp/wt-implement status --porcelain # note anything left uncommitted
pi-sandbox exec --prompt-file /private/tmp/batch-42/review.prompt \
  --new-run-under /private/tmp/batch-42 --run-name review --timeout 1800 \
  -- --provider PROVIDER --model MODEL --tools read,bash
# (run from /private/tmp/wt-implement)
git -C /private/tmp/wt-implement status --porcelain # must match the pre-review state

# Revision: resume the implementer in its original worktree.
pi-sandbox exec --prompt-file /private/tmp/batch-42/revise.prompt \
  --resume-session /private/tmp/batch-42/implement-01/sessions/session.jsonl \
  --new-run-under /private/tmp/batch-42 --run-name implement --timeout 1800 \
  -- --provider PROVIDER --model MODEL
```

Because the namespace is declared in the manifest, none of these commands need
`--namespace`; all of them mount the same authenticated home. If the manifest
does not declare one, pass the same `--namespace NAME` to every command above.

Build artifacts are worktree-local: `target/`, `node_modules/`, and similar
directories are not shared through the home, so each fresh worktree rebuilds
from scratch. This is the main cost of extra worktrees, and another reason to
review in the implementer's. For Rust projects, point `CARGO_TARGET_DIR` into the shared home
from the manifest so every worker reuses one compiled graph; Cargo's build lock
serializes concurrent access. Manifests generated by `init --with rust` or
`--with tauri` already contain this; add it to older manifests:

```toml
[run.env]
CARGO_TARGET_DIR = "/tmp/pi-home/.cache/cargo-target"
```

Tell workers not to run `cargo clean` or delete cache directories when a cache
is shared.

## Worktree and branch rules

- Record the base commit before starting.
- Use unique branches and distinct worktree roots for workers that may overlap
  in time.
- Give every worker that should share provider credentials and home-installed
  dependencies the same explicit namespace. That namespace also shares mutable
  package caches and install locations: authenticate and provision dependencies
  before parallel work, and serialize `bundle install`, `npm install`, or other
  package-manager operations that could write the same shared state.
- Keep one owner for an implementation area. Multiple reviews are safe, but
  reviewers that run at the same time need distinct worktrees; overlapping
  writers create avoidable reconciliation work.
- Treat worker commits as candidates. Do not merge merely because a run says
  `completed`.
- Preserve unrelated pre-existing changes and make the integration action
  explicit: merge, cherry-pick, request another revision, or stop.
- A worker's `git status` describes its own worktree as seen from its
  container; verify host state from the host, not from a worker's report.
  When a reviewer shares the implementer's worktree, compare
  `git status --porcelain` before and after the review.

## Task-specific controller

For multiple stages, write a small Python controller in a private directory
outside all worker worktrees and place run artifacts there. It should:

- set a restrictive umask;
- invoke subprocesses with argument arrays and explicit working directories;
- write prompts and both streams to private regular files;
- propagate SIGINT and SIGTERM to active launchers;
- attempt targeted `pi-sandbox stop` if bounded shutdown fails;
- parse each `result.json` and retain every artifact;
- make dependencies explicit instead of launching review too early;
- stop before destructive integration or external side effects that were not
  authorized.

Copy `assets/orchestrator.py` beside the controller and import it from there.
Importing it in place from the installed skill directory is also fine, but set
`sys.dont_write_bytecode = True` (or `PYTHONDONTWRITEBYTECODE=1`) before the
import so no `__pycache__` lands in the checked-out skill. Adapt its main flow
to the task instead of rebuilding process supervision from scratch. The
controller may use `exec` for each stage and `--resume-session` for implementer
revisions. Use RPC only when live steering materially improves the workflow.

## Monitoring a running worker

`events.jsonl` is a durable protocol log, not a progress view: it is dominated
by token deltas and partial tool output. Use `status` instead of parsing it:

```sh
pi-sandbox status --batch BATCH            # one line per run directory
pi-sandbox status --output-dir OUTPUT --json
pi-sandbox status --batch BATCH --watch    # redraw until every run is terminal
```

A running line names the tool call still executing (`bash: cargo test --lib`)
or `awaiting model`, how long `events.jsonl` has been quiet (`idle 2m10s`), and
the last assistant text. A terminal line shows the exit code, the reason when
not `completed`, cleanup state, and the last `stderr.log` line for failures.
The `--json` form carries the same fields (`state`, `status`, `phase`, `tool`,
`idle_ms`, `last_text`, ...) for a controller that narrates progress.

`response.txt` and `result.json` appear only at the end; their absence means
the worker is still running or the launcher died. A long `idle` during a tool
call that should be quick, with a quiet `stderr.log`, is the stuck-worker
signal; run `status --inspect` to have Docker confirm the container is alive
before deciding.

## Failure handling

Reconcile the filesystem, Git branch, recorded commit, result, and cleanup state
before deciding what to do after a failure. A safe retry has a new output
directory and a prompt that explains the observed state; `--new-run-under
BATCH --run-name NAME` allocates `NAME-02`, `NAME-03`, ... without editing
controller paths, and prints the chosen path as the first stderr line. Bound
retries and escalate recurring failures rather than looping indefinitely.

A startup failure that mentions credentials or a missing API key is a namespace
problem, not a retry candidate: check the `persistent home:` line the launcher
printed, compare it with `pi-sandbox namespace show`, and fix the namespace
before launching again.

### Reading a failed run

A worker that stops short does not hang: the launcher exits non-zero and
writes `result.json` with `status: failed` and a `reason`. When the stop was
the model's, the transport's, or the container's doing, `result.json.error`
(also on the `run_finished` stdout envelope and in the `status` line) says
what happened and what to do, without anyone reading `events.jsonl`:

```json
"reason": "agent_error",
"error": {
  "class": "provider_capacity",
  "recovery": "resume",
  "recoverable": true,
  "message": "Selected model is at capacity. Please try a different model.",
  "provider": "openai-codex", "model": "MODEL"
}
```

`recovery` is the one autonomous move to make next. `recoverable` is its
shorthand for `resume`. Neither means the worktree is untouched: resume
restores the conversation, not files, so the worker (or you) must check
`git status` first.

### The escalation ladder

Make exactly one move per rung, and escalate to a human when the same class
recurs after it. Never make a second attempt of the same kind.

| `recovery` | Classes | Autonomous move | Escalate when |
| --- | --- | --- | --- |
| `resume` | `provider_capacity`, `rate_limit`, `transport`, `stream_interrupted` | Wait (30s, 2m, 5m), resume the session as it is. After repeated `provider_capacity`, resume with a fallback `--model` if one is agreed. Do not add parallel workers on the same account while rate-limited. | Attempts are exhausted, or the fallback model is also at capacity. |
| `resume_adjusted` | `timeout` | Look at `status` for the last tool call: if the worker was stuck on one command, name it in the prompt. Resume once with `--timeout` doubled and a prompt that says to finish and commit verified work first. | A second timeout, or the same command hangs both times. |
| `resume_adjusted` | `worker_exit`, `aborted`, `unknown` | Read `stderr.log` / the message. Resume once; a resume does not replay actions, so the cost of a wasted attempt is low. Note an `unknown` message so the classifier can learn it. | It recurs, or stderr shows out-of-memory or a broken image. |
| `restart` | `context_overflow` | Start one fresh session from a handoff prompt: the original assignment, `git status`/`git log`/`git diff --stat` from the worktree, and the old session's last report. Tell it to keep its context small. | The fresh session also overflows: the assignment needs splitting, which is a scoping decision. |
| `fix_environment` | `auth` | Run `pi-sandbox namespace show` for the worker's namespace. If it reports credentials present, the failure was probably a token refresh: resume once. If the run used a different namespace than the credentialed one, that is a configuration bug to fix. | Credentials are absent or expired: only a human can log in (`pi-sandbox run --namespace NAME`). |
| `escalate` | launcher errors, `cleanup_failed`, protocol errors, missing result | Confirm Docker is alive (`status --inspect`, `docker info`). | Docker is down, or the container cannot be removed. |

The human-only set is therefore small: expired credentials, a broken Docker
daemon, an assignment too large for one context even when fresh, and any
failure that recurs after its one adjusted attempt. Everything else has one
well-defined move. When you do escalate, report the run directory, the
class, the message, and which moves were already made.

### Resuming by hand

From the same worktree the failed run used:

```text
SESSION=$(python3 -c 'import json,sys; print(json.load(open(sys.argv[1]))["session_files"][0])' BATCH/implement-01/result.json)
git -C /private/tmp/wt-implement status --porcelain      # note what the worker left behind
pi-sandbox exec --prompt-file /private/tmp/batch-42/resume.prompt \
  --resume-session "$SESSION" \
  --new-run-under BATCH --run-name implement --timeout 1800 \
  -- --provider PROVIDER --model MODEL
```

`resume.prompt` should quote the error and tell the worker to run `git status`
and `git log` before continuing its original assignment. For a `restart`,
omit `--resume-session` and write the handoff prompt described above.

### Recovering from a controller

`run_with_recovery` in `assets/orchestrator.py` walks the ladder for you: it
follows `error.recovery` after every attempt, resumes or restarts in a fresh
`NAME-NN` directory, applies backoff, doubles the timeout once, builds the
handoff prompt, checks credentials before giving up on `auth`, bounds the
total number of runs, and logs one line per decision so the orchestrator
narrating progress sees why a worker restarted.

```python
attempts = run_with_recovery(
    worker,
    output_root=output_root,
    namespace="feature_orchestrator",
    timeout=1800,
    pi_args=["--provider", "PROVIDER", "--model", "MODEL"],
    max_attempts=4,
    backoff_seconds=(30, 120, 300),
    fallback_pi_args=["--provider", "PROVIDER", "--model", "FALLBACK_MODEL"],  # optional
)
outcome = attempts[-1]
if outcome.escalation:
    ...  # tell the human: outcome.describe_failure(), outcome.output_dir
require_completed(outcome)   # raises with the class, message, and escalation reason
```

The final outcome's `escalation` is set only when a human is needed, and says
why. A completed resume or restart is still a candidate to review like any
other run.
